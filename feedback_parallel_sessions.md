**Do this VISIBLY at session start** — after reading CURRENT_TASK.md, state in one line whether the work splits into parallel tracks and why/why not. The user reminded me 2026-07-20 that I evaluated it only silently; the assessment must be surfaced, not just internal.

When CURRENT_TASK.md (or the user's ask) contains multiple substantial, independent sub-items, evaluate splitting the work: this session works directly in a git worktree (via EnterWorktree) on one track, and a background Agent with `isolation: "worktree"` handles another track in parallel.

**Why:** confirmed with the user 2026-07-14 after a live comparison. A background agent's exploration/edits happen in a fully separate context — they never enter the main session's context, so the main session avoids early compaction. Worktree-isolated tracks also run in true wall-clock parallel, so total completion time drops. This is strictly better than doing both tracks sequentially in one context, for tasks large enough to matter.

**How to apply — only worth it when:**
- Each sub-item is big enough to need real file exploration/editing on its own (not a one-liner).
- The sub-items don't require tight interactive back-and-forth with the user. If an item is explicitly framed as "let's decide together" / a joint discussion (see e.g. spam/SEO-risk item in [[project_zero_touch_selfservice]]-adjacent work), keep it in the interactive session — don't hand it to a cold background agent that can't have that conversation.
- Minor file overlap between tracks is fine — worktree branches only conflict at merge time (normal, resolvable), never at runtime, since each worktree is a separate checkout.

**Don't split:** small or single-file asks, or genuinely tightly-coupled work where the overhead of worktree setup + writing a comprehensive self-contained cold-start prompt exceeds the savings. This rule coexists with [[feedback_token_efficiency]] and [[feedback_no_overthinking]] — those already caution against unneeded subagents; this is specifically for multi-part, CURRENT_TASK.md-scale work, not every session.

**The split criterion is CONCEPT, not item count — learned the hard way 2026-07-31.** Three sessions ran in parallel in the SAME tree (no worktree): ads/charts, store freeze-close, and the admin money log. They read as independent lines in CURRENT_TASK.md, but "הקפאת/סגירת חנות" changes *what a store IS*, so it rippled into checkout, cart, orders, the seller dashboard and `translations.ts` — the same files the ads session was editing. Result: the shared tree went red repeatedly from the other session's half-written refactor (`blocked` → `discoverable`, `blockedOnly` → `state`), and my own `verify` runs kept failing on files I never touched. **Ask "does this task redefine a core noun — store, order, product, money?" If yes it runs ALONE, and the rest go in parallel after it.** Different corners of the app (ads vs admin money log) parallelise fine. **And once code is written to shared files, a worktree no longer helps** — worktrees separate work *before* it exists, so the decision must be made and stated at session start (the visible rule at the top of this note) or not at all; never pull a long-running session into one. The user's framing when it went wrong: *"אם צריך work tree אתה זה שאמור לפעול בנושא"* — it is my call to make and announce, not a question to hand back.

**Two sessions in ONE tree is now forbidden, not merely risky — diagnosed 2026-08-04 after the user reported both sessions hanging forever at the end of the checks.** It is not contention, it is a loop with no exit: every gate here keys off a fingerprint of the *whole* working tree (`verify.mjs`'s content hash, `review-state.sh`'s `diff_fingerprint`), so the other session's keystroke (a) voids the "unchanged since it last passed" cache so every Stop hook pays the full suite, (b) resets `require-green.sh`'s `red-$fp` counter to 0 so its 2-attempt escape hatch never fires, and (c) makes `--all` red on half-written code the session doesn't own and can't fix — it edits, the fingerprint moves, a fresh gate opens, red again. Plus shared writers on `node_modules/.cache` (eslint — which already has a false-RED history — tsbuildinfo, the PGlite image) and ~20 heavy processes on 12 cores against a 240s hook timeout. Earlier notes called this survivable if the files were disjoint; **that was wrong — the files don't have to overlap, the fingerprint is the whole tree.** The fix (chosen by the user, built same day): a worktree per session + `npm run worktree:setup` as its first command — `scripts/worktree-setup.mjs` clones `node_modules` by APFS reference (~10s, ~0 disk), drops the cloned `.cache`, and copies `.env` + `.claude/settings.local.json`, all of which a checkout lacks. Still true from 2026-08-02: multi-second timeouts in files you never touched are contention, not a defect; and commit per topic ([[feedback_commit_granularity]]).

**The two things worktrees CANNOT isolate, both hit 2026-08-05:**
1. **A migration number.** Isolation is exactly what stops each side from seeing the other's next number, so both sessions wrote `0010_*.sql`. The runner orders by filename, so two `0010`s both run, in an order neither author chose. Before adding a migration, check `git ls-tree --name-only main migrations/` — not just the local directory — and renumber past whatever landed first (the later branch moves; `git mv` + re-run `npm run db:migrate`).
2. **Me, using git to "compare against the base".** I ran `git checkout main -- .` inside my worktree to control-test a failing check, and it overwrote the whole working tree with main's content — including files from the other session that don't exist on my branch. The worktree did its job; the command undid it. **Never `git checkout <ref> -- .` (or `-- <file>`) to inspect another ref** — use `git show <ref>:<path>`, `git diff <ref>`, or `git log <ref>`, none of which touch the working tree. If a check fails and you suspect it isn't yours, read `git log main` first: that session's fix may already be there (it was).

**A new worktree does NOT necessarily start on `main` — check, every time (2026-08-05, hit twice in one session).** `EnterWorktree` branches from whatever the repo's HEAD/base resolves to, and in a tree where several sessions are live that was ANOTHER session's merge commit — so the first worktree opened 10 commits behind local main, and the second opened on top of an unfinished view-transitions branch. `git log --oneline -1` immediately after entering, and if it is not main, `git checkout -B <branch> main`. (`git reset --hard` is permission-blocked here; `checkout -B` does the same job.) **Related, same session: main WILL move under you.** Four other sessions merged into main mid-task, twice making my merge non-fast-forward. `git merge main` into the worktree, re-run `verify -- --all`, then ff main — never force it.

**Two ways a parallel session can DELETE merged work, both hit 2026-08-06 in one session — and both were silent.**
1. **A session committing from a stale working tree reverts everything merged since.** Another session committed a docs change from a tree that predated my merge, so its commit's TREE carried the old state of 24 files: four new test suites and a whole new module came back out, on main, with a green-looking commit whose message mentioned only the doc. Nothing warns about this — `git commit -a`/`add -A` writes what is on disk, and a checkout whose HEAD moved under it (see below) has the wrong thing on disk. **After main moves under you, and before ANY commit in the shared checkout, `git status` must be clean-and-current** — if `git log` shows commits whose files are missing from disk, the index is stale and a commit will revert them. Recovery is `git checkout <good-sha> -- <paths>`, path by path so the other session's real change survives.
2. **`git update-ref refs/heads/main <branch>` discards whatever main gained meanwhile.** I used it because `git push . HEAD:main` timed out, and it silently dropped another session's merge (recovered — every commit was still reachable). It is not a fast-forward; it is an assignment. **Always `git merge-base --is-ancestor main <branch>` first**, and save `git update-ref refs/rescue/<name> <sha>` anchors before any ref surgery — that is what made this fully recoverable.

**A worktree gets its OWN memory directory, and until 2026-08-06 nothing pointed it anywhere.** The harness derives the memory path from the absolute project path, so a worktree's slug differs from the main checkout's; `setup-claude-memory.sh` only ever linked the latter. Memory written from a worktree landed in a directory belonging to no repo, and the sync then walked up, found the PROJECT repo, and committed a tree of memory files — no `src/` — onto the session's own branch. Pointing main at that branch is what took main's tree with it. `scripts/worktree-setup.mjs` now symlinks it; if a worktree ever reports `memory: skipped`, stop and fix that before writing memory.

**Practical gotcha — this BIT US 2026-07-20:** a new worktree branches from `origin/<default-branch>` by default (`worktree.baseRef` setting, default `fresh`), not from local HEAD or uncommitted changes. That session origin/main was 2 commits behind local HEAD, so the background agent built the admin-performance tab on a stale codebase; its edits to shared files couldn't be merged (would revert current features) and had to be re-applied by hand to current HEAD instead (its `PerformanceSummary` was even missing a since-added field). **Before splitting: check `git merge-base HEAD origin/<default>` — if origin is behind, the worktree will start stale.** Either push local commits first (user-gated — confirm), or, if pushing isn't wanted, don't split and do the item inline. If a split already ran from a stale base, verify the agent's new files against CURRENT signatures before integrating, and never `git checkout <agent-branch> -- <shared-file>` (it clobbers current work).
