**SUPERSEDED ON SHADOWS (2026-08-01).** The tiered "tactile depth" rule this memory used to describe — lone/hero surface = 1.5px + `--shadow-card`, repeated card = 1px + `--shadow-xs`, both at REST — is gone. It asked how *important* a surface was, the answer was always "a bit", so a shadow ended up on nearly everything: an audit that day found 279 declarations, and the hover shadow had stopped reading as a change because rest was never empty.

**The rule now:** a shadow means "this surface FLOATS above the page". Only something that genuinely floats carries one at rest — dropdown, modal, toast, drawer, sticky/fixed bar, a badge or arrow overlaying content. Anything in normal flow (card, tile, hero product image, page section, chip, table row, store banner) is `1px --color-border` on `--color-surface` and nothing else, taking depth on **hover** only if it is clickable. Pressed/selected = fill + border + weight, never a shadow as a third signal. Written in full on the tokens in `src/styles/base/tokens.css`; enforced mechanically by `tests/design-shadow-rule.test.ts`, which scans `src/**` and fails a new at-rest `--shadow-xs`/`--shadow-card` unless its selector is on a FLOATING allowlist *with the reason it floats*.

**The overlay half, finished 2026-08-02.** The rule above governed surfaces that DON'T float; the ones that do had never been unified — 18 hand-rolled `rgba(0,0,0,…)` declarations (blur 14→60px, opacity 6→22%) in **pure black**, while every token is the site's blue-grey ink `23,27,38`. The user's read was "ההצללות של ההדר ושל הוילון זולות, לא מודרניות", and the diagnosis: the header was already fine (border at rest, `--shadow-bar` only once scrolled), the *drawer* was the cheap one — pure black, 40px bloom, on top of a scrim already doing the separating. Two new tokens: `--shadow-overlay` (dialog over a scrim, downward bias) and `--shadow-sheet` (panel slid in from a viewport edge — offsetless on purpose, since three of its four sides are off-screen and the old file kept a separate value for LTR, RTL and mobile). Menus/popovers/toasts stay on `--shadow-card`. Both new tokens are deliberately OUT of the guard's scan, documented in the test: they are named for populations that float by definition. The guard's markup half now asks whether the element is positioned out of flow (looking across the whole opening tag) instead of allowlisting whole files.

Triggered by the user asking whether shadows had been overdone (product image, cards, chips) and then: "design elements are supposed to be functional and meaningful." That sentence is the general principle — see [[feedback_clean_design_line]].

**Still true, unaffected by the re-scope:**
1. **Scope per-page, don't touch the shared `.card` base class.** Page-specific selectors (`.home-product-card`, `.product-card` in store.css) keep blast radius contained.
2. **`translateY(-5px)` on homepage card hover is a deliberate mall-vs-store differentiator, not an oversight** (user, 2026-07-07: "צריך בידול בין אתר חנות לאתר הבית של הקניון"). The store page's `.product-card` stays flat because its image already zooms. Don't "fix" the asymmetry.
3. **A full-width list ROW signals hover with a border-color tint, never a shadow lift** — the hover shadow is calibrated for spaced grid cards and reads heavy on rows stacked 0.75rem apart (user called it "excessive", 2026-07-07). (Token renamed 2026-08-01: `--shadow-card-hover` → `--shadow-hover` / `--shadow-hover-deep`.) Applies to the buyer dashboard's `.o-card`, table rows, order cards.
4. **Qty steppers stay flat everywhere**, and the lesson that found them: **grep inline styles, not just CSS files** — this codebase has three independent quick-view modal implementations (PQV component, store page's own, product page's related-card one) sharing no markup, so a page-scoped CSS rule silently never reaches the other two. Same blind spot as [[project_transparent_image_bg]].
5. **The frameless product card was BUILT AND REJECTED ON SIGHT, 2026-08-04.** Border+radius+hover-shadow moved onto the image tile, body on `--color-bg` with no panel, accent-filled qty+cart pill, `line-clamp-2` on the name — applied to the store grid only, then reverted the same hour. The user's words: the accent CTA "לא שייך, משתלט על כל העמוד, לוקח את כל הפוקוס" (a full-width saturated pill on every card = a wall of blue), and the card had drifted too far from the product page and the quick-view modal, which still carry `.card`. **The transferable lesson, and it is the same one as the deep-shadow rejection above: a treatment must be judged on a full grid, not on one card** — the CTA looked right in isolation and read as noise repeated eight times. Don't re-propose the frameless card without solving the CTA and the other three surfaces together. See [[feedback_clean_design_line]].
6. `.m-card--unread`'s accent stripe is an `inset` shadow — a mark drawn ON the card, not elevation, so the flat-at-rest rule leaves it alone.

**The hover side, settled the same day.** Two tokens, because a shadow is cast by a GAP: `--shadow-hover` (surface stays put) and `--shadow-hover-deep` (surface actually rises 4-5px). One value for both made the still card look like it was hovering in mid-air and the rising card look glued down. Both were also toned right down — the old single value was sized back when every card already had a shadow at rest and hover had to out-shout it; with rest flat, the change from nothing to something does the work.

**SIZE is not a second trigger for the deep one, and this was tested and rejected within the hour.** The product page's hero image got the deep token on the argument that the shallow one "disappears" across the largest surface on the site. The user rejected it on sight: on a site that is flat everywhere, a deep shadow reads as loud, not as proportionate. **The general principle, and it beat my reasoning twice in one session — restraint outranks legibility here.** A surface with no shadow at rest is already changing state when it gets any shadow at all; it does not also have to announce itself. See [[feedback_clean_design_line]].

**How to apply:** before adding any shadow, ask only one question — does this surface cover content beneath it? If no, there is no shadow to add. If it is clickable, the hover state is where depth goes, and it takes the deep token only if it physically rises.
