3. **§9.5 found a real bug, and a count alone would have missed it.** 50 concurrent buyers, stock 10: exactly 10 succeeded — but **7 of the 40 refusals reported up to 8 units left when the true stock was 0**. A CTE reads the snapshot from statement start; the `UPDATE` beside it, blocked on a row lock, re-reads when the lock releases. Under contention they disagree, and that stale number is what the buyer's page clamps the quantity selector to. A refusal now re-reads in its own statement (`store-products.ts#stockAfterRefusal`), on the out-of-stock path only. **Assert that the winners' `after` values are all DIFFERENT, not just that there are ten** — ten successes reporting the same number means one unit sold ten times.
4. **`Seq Scan` at today's size is the CORRECT plan, so a naive §9.2 check reports a false failure.** Run each hot query twice — once normally, once with `SET enable_seqscan = off` — which is what actually answers "is the index usable". Measured crossover on `stores`: Seq at 45 and 200 rows, `Index Scan` from 1,000, and the cost is **flat** from there (8.29 at 1k vs 8.44 at 100k).
5. **The load ceiling was the NETWORK, not the database — and the arithmetic is worth remembering.** A page load is 1 read + 4 unawaited writes = 5 queries. At 500 concurrent: zero failures, no pool exhaustion. Throughput ≈ `pool(10) ÷ RTT ÷ 5`, which at the measured 66ms laptop→Frankfurt RTT is the ~30 loads/s observed exactly. Co-located (production) that is three orders of magnitude of headroom. **The one high-return change left: batching those four writes into one statement takes a page load from 5 round trips to 2.** Also verified: the error path's `MAX_CONCURRENT_WRITES=2` really does hold under a 50-request storm and releases the slot even when the write *throws* (without that, an outage silences the log forever), and `console.error` is ~200k/s, not a bottleneck.

**What the `stores` module added (2026-08-02):** a `citext` column makes uniqueness case-insensitive, which is wanted — but RESOLUTION must stay case-SENSITIVE, or one store sits at every capitalisation of its name and they are all duplicate content. A `Partial<>` update against SQL must build its `SET` from `Object.keys`, not from the values: a key present with `undefined` means clear, an absent key means don't touch, and read-modify-write instead is the record-rev bug. And a JS list written to rows keeps its order only if something orders it — `unnest(...) WITH ORDINALITY` with a per-position offset, since all the rows share one `now()`.

**What the `store-categories` module added (2026-08-02), and both items generalise to every remaining module:** (1) **An `await` inserted into the middle of a JSON read-modify-write is a lost update.** `bulkUpsertProducts` was `readProducts()` → mutate → `writeProducts()` synchronously, i.e. atomic within the process; adding one awaited query in the middle opened a window where two concurrent CSV imports each report success and the second erases the first's whole catalog. The fix is ordering, not machinery — hoist every `await` above the read and keep everything below it synchronous. A microtask-level test reproduces it. **Check this in each module before declaring it done.** (2) **A `maxlength` on an input is not a rule** — once a name is in a btree index, an oversized one stops being a silly value and starts raising (index-tuple size limit), i.e. a 500 on a form that used to work; the cap moved server-side (`MAX_CATEGORY_NAME_LENGTH`), rejecting in the single-field editor and truncating on the bulk/CSV path.

**What the `store-products` module added (2026-08-02) — the module with the worst coverage of the four so far:** its entire behavioural coverage was two pure functions plus a `decrementStock` group running against a mocked `node:fs`; everything else that touches a product mocks the module wholesale, so a swap returning an empty catalog for every store would have left 123 test files green. (2) **A partial map needs a NULL, not a 0.** A combo carrying only a SKU had to be stored `stock = 0`, which reads as "sold out" rather than "no override" — a whole colour would have stopped being purchasable the moment the catalog moved. `migrations/0003` makes the column nullable; a test fails without it. (3) **What replaces "hoist every `await` above the read" is a transaction, not a reordering.** `bulkUpsertProducts` is one transaction that reads the catalog INSIDE itself; a per-row loop of `createProduct`/`updateProduct` would be a thousand transactions and a file failing on row 600 leaves 599 products behind. Where a whole snapshot IS the wire contract (the sync endpoint, because `localStorage` is the other authority), write it as a **diff**: `ON CONFLICT … DO UPDATE … WHERE IS DISTINCT FROM`, so a qty change is one `UPDATE` of one row. 5. **A seeder half that generates data is different from one that carries data across.** Here it really did seed favourite/wishlist counts into two JSON files (one with no live reader, one keyed by the wrong thing), so demo dashboards showed zeros while the script printed success. They are rows now inside `writeCatalog`'s transaction — and with that the demo seeder stopped touching `fs` entirely.

Also: **verify the §9.7 anchors by BREAKING them, not by finding them.** All five buyer-state import paths were broken one at a time (including re-introducing the exact 2026-08-02 wishlist-key bug) and `tests/db-import.test.ts` went red for each.

**What the advertising three added (2026-08-02) — `ad-campaigns` + `brand-campaigns` + `platform-ads` in ONE diff, because [[project_brand_boost_twin_drift]] says a fix to one campaign kind without the other IS the drift.** Coverage before, measured by stubbing each module's I/O to return nothing: **1784/1785, 1781/1785, and 1785/1785 green** — the third had no test file at all. The two files that *looked* like coverage were mocks of the module under test (`vi.doMock` of `ad-campaigns`, `vi.mock('node:fs')` in `store-lifecycle`); both were rewritten against the real table with **no mocks left**. Six things worth carrying forward:

1. **Check whether the target already exists before treating it as an open decision.** `platform-ads` and `admin-tab-views` were recorded as "no table, needs a decision" — but `0001_init.sql` already creates `app_settings(key, value jsonb)` with a comment naming both, and `db-import.mjs` already wrote to it. The plan's prose had gone stale, not the schema. **Read the migration, not the plan's summary of it.**
2. **A jsonb value has no column type and no CHECK, so the validator IS the constraint.** Money in `app_settings` gets neither `bigint` range nor `>= 0` from the database; `coerce()` runs on every read AND every write instead. Until this diff the route took any finite number, so `1e30` was a valid lifetime budget. If a value in there is money, it needs an explicit cap in code — decide this deliberately rather than inheriting it.
3. **`mutex.ts` had ZERO importers and had for a while.** The plan said seven files imported it; all seven merely *mentioned* it in a comment (`grep -l` on the word, not on an import). Deleted in this diff. **Grep for the import form, never the name.**
4. **`+=` is the only bigint hazard, and here it was real.** `admin-ads.ts` sums campaign budgets — `'30000' + '20000'` is `'3000020000'`. Division (`fromAgorot`) coerces and is safe, which is why exactly one test needs a stub driver answering the way `pg` does.
5. **`NOT NULL DEFAULT '{}'` means a reader written against the file gets `[]` where it expected `undefined`.** Array columns are mapped back to `undefined` on read so every existing caller's truthiness check still means what it did.
6. **The write-inside-a-loop is the N+1 that this kind of module creates.** A read that sweeps (`getCampaignsForStore`) now decides in memory and writes once per **kind** — at most four statements however many campaigns — and closing a store archives them all in one. As files these loops were invisible.

Also: **a batch sabotage runner can lie.** 23 mechanisms were broken one at a time and 23 were caught, but one first reported "survived" — Vite had cached the module between two edits landing in the same second. Re-run a survivor in isolation before believing it.

**What `error-log` + `admin-tab-views` added (2026-08-02) — the last two modules, one diff, no money. Coverage before, measured: stubbing both to return nothing left 1825/1825 green in 147 files.** Five things worth carrying forward:

1. **A logger that becomes a query inside the error handler must give up fast, not wait — and the reason is the POOL, not the log.** `middleware.ts` catches every 500 and calls `logError`, so when the database is what broke, *every* request runs it: awaiting there parks a pooled connection per failing request until timeout, and a DB outage amplifies itself into a frozen site. So `logError` never rejects, all ten call sites are `void logError(…)`, and a `MAX_CONCURRENT_WRITES` counter caps how much of the pool the module can hold — dropping past it, never queueing. **A `Promise.race` timeout does NOT do this job: it abandons the promise while the query keeps the connection.** A dropped entry still goes to `console.error`, which is where external monitoring reads anyway. Same call, `resolveErrorContext`'s three queries moved *inside* it, so no `await` is left on the error path.
2. **A ceiling that was `slice(-N)` on a file is a ceiling on the TABLE, not a `LIMIT` on the read.** They sound interchangeable and are not: `LIMIT` bounds what the admin sees, not what the table costs, and `/api/log-client-error` is unauthenticated *and* unrated. Enforced in the write statement. And the NUMBER stays 500 because two readers derive exactness from it (the store-filter dropdown and the "(N) new" badge are computed over `getRecentErrors(MAX_ENTRIES)`); raising it turns both into "over the newest N" silently. **When a cap moves from file to table, ask what reads the whole array before changing the number.**
3. **`OFFSET` inside a data-modifying CTE is `cap - 1`, not `cap`** — every part of such a CTE sees the same snapshot, so the `DELETE` cannot see the row the `INSERT` beside it writes.
4. **A timestamp is not arrival order, and a test found it where reading the code did not.** `now()` has finite resolution — three back-to-back writes landed on one millisecond, tie-broken by a random uuid. Cosmetic for a list; **not cosmetic for a ceiling that deletes by that order**, since a burst could evict an entry newer than one it kept, and a burst is exactly when a ceiling runs. `migrations/0005` adds `seq bigint … AS IDENTITY`. **Any append-only table whose order carries meaning needs a sequence, not a clock.**
5. **A grep guard test can find a copy you never looked for.** The one written here (no second literal `['sellers','stores','orders','alerts']` in `src/`) immediately found a **third** copy in browser code (`src/scripts/admin/tab-nav.ts`). That copy is also why the list now lives in `lib/admin-tabs.ts` with **zero imports** — `admin-tab-views.ts` imports the database and can never be bundled for a page. **When extracting a shared rule, check whether a client bundle needs it too, or the extraction only merges two of three copies.**

Also, twice over: **sabotage per mechanism keeps paying.** 21 mechanisms, all 21 caught — but two only on a second pass. One "survivor" was a bug in the sabotage script (the replacement hit the first occurrence of the string, which was in a *comment* above the SQL — target something unique to the code); the other exposed a test of mine that verified nothing, because it asserted on an `undefined` field the context never resolved anyway.

**✅ §3 DONE (2026-08-03, branch `db-stage-getall`) — and the ONE rule it settled, which applies to every reporting change from here:** *a `GROUP BY` written as a `for` loop belongs in the database; arithmetic takes its data as a parameter and stays synchronous.* Same split the page-view and analytics moves made. Full detail in DB_MIGRATION_PLAN.md §8; what is worth carrying forward:

1. **Every pure function that left the render path became the query's TWIN, not dead code.** `filterAndSortOrders`, `getStoreRevenueMap`, `getOrderTotals`, `reconcileOrders`, `buildSellerFunnel`, `buildPlatformSales`, `campaignTotalsOf` — all kept, all still unit-testable with no database, and `tests/reporting-invariants.test.ts` §7 runs each against its query over the same rows. That section is the reason "the SQL still means what the JS meant" is a thing a test can say instead of a hope. **Do this for the next one too:** a SUM and a `reduce` agreeing is not obvious — they differ on rounding, on `bigint` arriving as a string, on which rows a LEFT JOIN keeps, and on which calendar decides a day.
2. **`astro check` catches what `tsc --noEmit` cannot: the `.astro` TEMPLATE body.** With every frontmatter clean and `tsc` silent, `astro check` found 12 dead references in the markup (`allOrders.length`, six order-filter variables, the messages list). **`npm run verify -- --all` is the gate, `tsc` is not.**
3. **A COUNT that was `array.length` is a silent bug the moment the array becomes a page.** `totalAll={allOrders.length}` and a seller card's `products.length` would both have collapsed to "page size" without a word. Any list that gains paging: grep for `.length` on it.
4. **A parameter the statement does not mention is a bind ERROR, not a spare.** One param list shared by a COUNT and a SELECT → `bind message supplies 6 parameters, but prepared statement requires 5` on every load of the tab.
5. **Narrow with a SUPERSET when the exact rule is subtle.** Campaign date overlap (`ad-metrics.ts#overlapDays` — pause clamp, duration clamp, start clamp) is not worth a second copy in SQL on numbers the owner reads as money. The query only has to never DROP a row; anything extra scores zero in the JS and changes no total.
6. **`::date` on a `timestamptz` reads the SESSION's timezone.** Where the JS compares `createdAt.slice(0,10)` (UTC), write `(col AT TIME ZONE 'UTC')::date` explicitly. Reports bucket on `Asia/Jerusalem`; signup dates were left UTC deliberately and that inconsistency is written down rather than silently "fixed", because it moves a money figure.
7. **A Hebrew text rule ported into SQL needs a character-for-character guard test.** `normalizeHe` → migration 0006's `product_search_text()`. The final-letter fold is what makes "טלפון" find "ספר טלפונים"; a raw `ILIKE` fails exactly the Hebrew cases the normaliser exists for, silently. A generated column also needs an IMMUTABLE **function** — `array_to_string` is not marked immutable, so the expression cannot be inline.
8. **A live reconciliation should return only the rows that DISAGREE**, with a cap and a `truncated` flag: a systemic bug makes every order disagree, and a banner quietly showing the first fifty understates the one situation it exists to shout about.
9. **Sabotage found two vacuous assertions again.** The funnel's `deleted_at` filter and reconcile's discount check both survived sabotage because the fixture has neither a deleted store nor an over-discounted row — fixed by having the tests create the damage and heal it.

**What stayed on purpose, and it is a decision:** `getAllStores()`/`getAllSellers()` are the admin ROSTER — every tab on that page is a list of it or a partition of it, cross-searched by seller name and sorted by a Hebrew `localeCompare` that a database collation is not. Everything DERIVED from it is a query now, so the page is O(platform) and no longer O(catalogue × stores). At 100,000 stores it needs SQL paging + a collation decision + a query per tab, which is a bigger job than §3 was.

**`GET /api/messages` with no params was DELETED, not paginated.** The reason it survived §8 ("maybe an external AI agent calls it") does not hold: it authenticates by SESSION COOKIE and the platform has no token auth and no public API. Paginating would mean designing a cursor for a consumer that does not exist.

**The money journal's free-text search stays in memory, and the blocker is not laziness:** it matches the Hebrew LABEL of an event type (which lives in code so there is one copy) and the amount as `formatAgorot` renders it (Intl). A column-only pushdown is a SUBSET, not a superset, because the halves are OR'd — it would DROP rows that match only by label.

**The journal's default window is 30 days (owner, 2026-08-03)** — it was the last unbounded read on the dashboard. The general lesson, for any list that gains a default narrowing: **a default is not a filter, and three things break silently without saying so.** (1) A permalink into the data now points outside the default — widen back to the row it names rather than reporting it missing, and resolve its day on the SAME calendar the window uses. (2) The empty state becomes a lie: "nothing recorded yet" and "nothing in this window" are different sentences and only one of them names the control that fixes it. (3) "Clear filters" must not offer to remove the default — that either lies (clearing lands on the same window) or hands back the unbounded read — and the control should NAME the default instead of showing values nobody chose.
