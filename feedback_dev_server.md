Never run `pkill`/kill the dev server, and don't start a new `npm run dev` instance to verify a change, unless the user explicitly asks for it.

**Why:** The user keeps their own dev server running persistently (they use it themselves) and doesn't want to run `npm run dev` repeatedly — killing it or spawning competing instances forces them to restart their own workflow. Said explicitly after I killed/restarted the server multiple times during [[feedback_testing_strategy]]-style verification.

**How to apply:** For UI verification (Playwright/browser checks etc.), check first whether a dev server is already up (e.g. `curl -sf http://localhost:4321` / `:4322`, or `lsof -i` for the astro/node process) and reuse that port — don't `pkill -f "astro dev"` and don't launch a fresh one. If no server is running and one is genuinely needed, ask before starting one, and never kill it afterward — leave it running for the user.

**You can take their server down without ever touching the process (2026-08-05 — the user asked "why do you keep crashing the server", and both causes were mine).** (1) **Deleting or renaming a module before updating its importers.** `rm src/lib/store-logo-plate.ts` ran while three files still imported it, and an `import` line was removed before the symbol it brought in; for that window Vite cannot resolve the graph and serves an error page instead of the site. Order every edit so the tree compiles at each step: update the importers first, delete last — same for a rename. (2) **Running `npm run verify` after every small step.** Eight full `--all` runs in one session is `astro check` plus eight vitest workers saturating every core, repeatedly, while their dev server needs some. This project already documented that exact contention in `vitest.config.ts` (a second session's dev server + migrations + `astro check` on 12 cores, producing a random subset of DB test failures every run). Run it once per coherent change, not per edit. The tests are NOT a suspect: they build their own throwaway Postgres and never touch the dev DB.

**A visual bug the user reports "on the site" may only exist in dev, and this one is intermittent by construction (measured 2026-08-05).** `curl` the dev server and the built server and count render-blocking stylesheets: dev serves **0** — the CSS arrives as `<style data-vite-dev-id=...>` injected by Vite's JS *after* the document parses — while the build serves exactly **1** `<link rel="stylesheet">`. So in dev, whether the first painted frame has any CSS at all is a RACE. When it loses, the first frame is unstyled chrome — icons at default size, badges unpositioned, the header not yet `position:fixed` — and then everything snaps into place. That is exactly what "האייקונים פתאום נעלמים או שהמספרים עליהם נעלמים ואז הם חוזרים, שבריר שניה… זה לא קורה כל הזמן, לא ברור מתי" describes, and it CANNOT happen on a build. **How to apply:** when a flicker/FOUC report cannot be reproduced, check where the user was looking before hunting the code — and give them the build command rather than a fix: `npm run build`, then `AUTH_SECRET=$(openssl rand -hex 32) ADMIN_SECRET=$(openssl rand -hex 32) PORT=4324 npm start` (production `npm start` refuses to boot without those two; `DATABASE_URL` comes from `.env`). Related: [[project_header_stability]].

**The cost of that reuse (2026-07-29):** a long-running dev server serves STALE `<script>` bundles. After adding an export to `lib/lightbox-image.ts` I measured the lightbox as broken — `neighbourIndexes is not defined`, and `watchCartPrices is not defined` from a module I never touched — while `tsc` and `astro check` were clean. Both symbols existed and were exported; the bundle was old. Worse, the failure was silent in the measurement: my Playwright assertions "passed" (17ms, cached!) because the viewer never opened at all. **A `ReferenceError` for a symbol that demonstrably exists, or a suspiciously perfect timing result, means the bundle — not the code.** Verify against the production build instead: `npx astro build` then run `dist/server/entry.mjs` on a spare port (4399), test there, stop that one when done. That's a server I started, so killing it is fine — the user's stays untouched. Tell them their dev tab needs a reload, since their own browsing is hitting the same stale bundle.
