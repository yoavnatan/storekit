## What we're building
Multi-vendor internet mall for the Israeli market. Sellers open stores; shoppers discover across them. Two independent SEO surfaces: platform (discovery) + each store (standalone feel).

**Vision:** Enable anyone to open an online store easily and efficiently — one that generates profit, is fair, and is fully transparent.

**Mission (north star):** Build a Hebrew-language digital shopping mall that removes the technological and financial barriers for small businesses through built-in automation, a clean minimalist management interface, and a fair, transparent pricing model. (Payment/pricing specifics — subscription tiers + split checkout — in *Business model* below.)

**Business model:** Hebrew digital mall. Buyer can pay **either** per-store separately **or** one unified charge for the whole cart (decided 2026-07-22 — both offered; unified needs the processor to split one charge across multiple sub-merchants, still to confirm with SUMIT/Takbull). **Pricing — IN CODE since 2026-07-27, `src/lib/pricing.ts` is the single source:** subscription **tiers** = fixed monthly fee + per-sale commission, higher tier = lower commission, charged **additively (not offset)**. Fees final, percentages still placeholder: Starter 99₪/12% · Growth 125₪/11% · Pro 179₪/10.25% · Enterprise 199₪/10%. Commission is **per-seller-account** (`Seller.tier?`), never a global config number — `store.config.ts` deliberately has no `commissionPercent`. **Invariant on ANY number change:** upgrade break-evens (fee delta ÷ commission delta) must RISE across tiers, else a middle tier is strictly dominated — asserted in `tests/pricing.test.ts`; the ladder is deliberately shallow, and the economics behind that (plus what was rejected) are in memory `project_business_model_pricing`. **Advertising is a fully separate component** — pay-per-actual-spend via Authorize/Capture (+ a disclosed platform margin), never offset against subscription/commission. **No time-boxed trial — the monthly fee starts at the seller's FIRST SALE, capped at 2 months from signup (decided 2026-07-29).** Card at signup either way (the ads Authorize/Capture needs it on file). A 14–30d trial sat in this spec from 2026-07-21 and was rejected on review: a trial promises the value lands inside its window, and at launch — few stores, little traffic — it cannot, so day 14 becomes a scheduled cancellation AND sends the seller away concluding "this doesn't work". Charging only once the mall has actually sold for him removes the decision moment entirely; the 2-month cap is what stops a dead store sitting free forever. Seller-facing wording is "קודם מוכרים. אחר כך משלמים." — never "התחילו בחינם", which is the Shopify script (see Positioning above).** (Supersedes the old "no fixed fees / success-based only" line.) **Sellers = registered businesses only** (עצמאים/עוסק פטור/מורשה) — not private individuals; matches the provider's sub-merchant requirement and differentiates from Israeli P2P marketplaces (My Product, Yad2), which serve private sellers via manual escrow, not a branded storefront + shipping + marketing. **Positioning in COPY (user, 2026-07-28):** the pitch is the mall, never store-building software — "open a store in minutes / no code / free to start" is the Shopify script and repeating it enters a comparison this platform loses. Lead with what a seller cannot get elsewhere: an Israeli digital mall, a store of your own, the pull of a mall, ads/SEO/shipping built in. Buyer-facing surfaces must never describe shoppers as something delivered to a seller ("a mall that brings you customers") — the homepage is a buyer's page first. **Fixed platform template only** — no per-seller site/theme design tooling, ever (deliberate scope boundary; the target seller wants zero design decisions and speed). **Zero-touch self-service** — the owner has no manual, ongoing involvement with sellers/buyers; every flow (registration, upload, fulfillment, messaging, disputes) defaults to fully automated, never owner approval — a scale requirement (see Hard rules → Scalability). Any new feature involving admin/manual gatekeeping must default to an automated equivalent instead.

**Target segment:** catalog stores with **dozens of products**, not 5–10-item boutiques. This fits the whole design — real catalog management (bulk tools) becomes necessary not optional, a large SEO surface (many indexable product pages) makes the discovery bet pay off, and product-first clean UX serves browsing/search/categories rather than the bespoke atmosphere a tiny boutique wants. "Clean & fast" reads as professional for a catalog, not "cheap" — the over-designed boutique is the wrong mirror to judge against.

### Payment architecture — decided (2026-07-06)
**Split payment via the payment processor.** Platform never holds seller funds — each seller has a sub-merchant account with the processor, which splits payment automatically at checkout (seller's share → seller, commission → platform). Reason: platform holding + manually disbursing seller money would be a regulated PSP service in Israel; split payment keeps the platform a pure software/marketplace layer.
- **Buyer pays per-store OR unified (decided 2026-07-22 — offer both).** Per-store = one charge per seller (independent refunds/cancellations, current cart UI). Unified = one card charge for the whole cart, processor splits it across all sellers' sub-merchant accounts. Both providers' split capability is already confirmed to exist; the only open detail for unified is that a single transaction splits across **multiple different sellers** (not just seller↔platform) — verify as part of the provider-selection task in CURRENT_TASK #1.
- Candidates: **SUMIT** and **תקבול (Takbull)** explicitly market a marketplace/split model. **Takbull is the leading pick (2026-07-22)** — it covers all four requirements: (1) unified cart (buy from several stores in one payment), (2) automatic split payment, (3) digital self-serve seller onboarding as sub-merchants, (4) regulatory-risk avoidance (platform never touches seller funds → not a PSP/נש"פ). Final commit still pending direct confirmation of terms. Cardcom/Payme/Tranzila/PayPlus/Meshulam are common gateways but sub-merchant split support unconfirmed.
- No manual payout queue — processor pays sellers directly, so admin never marks payouts "paid". `SellerBalance`/admin dashboard is a **reporting** view (totalEarned per seller) only.
- Commission % deducted at processor/order level (`store.config.ts` → `checkout.commissionPercent`).

## Architecture
- **Stack:** Astro 7 + Node adapter, TypeScript, Tailwind v4, self-hosted Heebo, `tokens.css` color system. Dev toolbar disabled. Astro 7's compiler rejects an HTML comment as the first child right after `{expr && (` — place comments above the expression, not inside it. **In a page this fails SILENTLY in dev:** the route stops building, so a static route falls through to a dynamic sibling — `/stores` started 302-ing to `/404` via `[storeSlug]` with no error anywhere, and `astro check` still reported 0 errors. A page that suddenly 404s/redirects after an edit is this, not a routing bug.
- **Fonts:** hand-written `@font-face` in `main.css` (not `@fontsource`'s per-weight CSS — trims unused subsets, still reuses its font files). `font-display:optional`, not `swap`. **All 10 weight×script combos (400-800 × hebrew/latin) preloaded in `BaseLayout.astro` (2026-07-16)** — preloading only weight 800 left every other combo to fallback-then-swap on first layout (real, measured layout-shift).
- **View Transitions — investigated, not adopted (2026-07-16):** `ClientRouter` is opt-out-per-link, not opt-in — enabling it soft-navigates the whole site by default (full `DOMContentLoaded`→`astro:page-load` audit either way). The JS-free native `@view-transition` CSS alternative was tried and reverted same session: its 4s renderable timeout was blown by a render-blocking font `<link>` (now fixed, see Fonts), stalling then snapping. Never re-verified since — don't assume it's safe to retry without a fresh check.
- **Prefetch:** Astro's built-in `prefetch` is on with `prefetchAll:false` + hover strategy — opt in per link with `data-astro-prefetch` (product page's "לחנות", `StoreCard`), never site-wide. It binds only to links present at load, so a link built later via innerHTML (the modal's "לדף המוצר המלא") can't use it — and `astro:prefetch`'s `prefetch()` refuses it too, since that URL IS the current URL while the modal is open. Back still beats any prefetch: bfcache restores with zero work.
- **Split:** content pages = static, seller/admin/api = SSR.
- **Header:** `position:fixed`; **height is pinned INLINE on `<header>`** (`height:3.4rem;box-sizing:border-box`) + `body{padding-top:3.4rem}` — never sticky, and the height must NEVER change (fixed inline so it can't flash-then-shrink before CSS/fonts load — the dev server injects CSS via JS after first paint; a `min-height` in header.css alone is too late). The logo (`.logo`, shared by the platform name AND a store name) is `display:inline-flex; line-height:1; font-size:1.3rem` so both render at the identical box/size in every context and the row height is logo-independent; the row itself is `.site-header .container{height:2rem}` (fixed, not min-height). Only the logo/store-name text is a click-to-home target — the rest of the row is inert. Desktop search sits flush after the logo (not centered) — confirmed 2026-07-09, don't re-center without asking. No entrance/pop-in animation on anything in `BaseLayout`/`Header.astro` — an MPA recreates those elements on every navigation, so the animation replays every time (removed one 2026-07-16 for this). Header row always renders `class="container"` (never the old `container between flex`) — every page passes `storeMode` (seller register/login/dashboard included) so row layout is one mechanism everywhere; row carries `min-height:2rem` (search input height) so icons center identically with or without a search bar. `.user-btn`/`.user-menu` pre-declared `position:relative`/`display:flex` rather than left to `spawnRipple()`'s static→relative promotion — the alert dot nests *inside* `.user-btn`, so a ripple-triggered position change on first click would've silently changed the dot's containing block (fixed 2026-07-16).
- **Footer:** ONE minimalist footer only — `Footer.astro` rendered once by `BaseLayout` on every page. Single row: `© year` + platform-name-links-home, then open-a-store (`/seller/register`) / terms / contact / lang-toggle. The old per-store second footer (`.store-platform-note` on store + product pages) was removed 2026-07-27 (two stacked footers + platform name ×3 = clutter) — don't re-add a page-level footer.
- **Data:** `data/*.json` dev-only; pure DB adapter functions, swap-ready for SQLite/Postgres.
- **Scroll:** never `window.scrollTo({top,behavior:'smooth'})` for a JS-computed target on this RTL site — native smooth-scroll visibly drifts `scrollX` off 0 mid-animation (off-thread, un-correctable via rAF). Use `animateScrollTo()` from `scroll-utils.ts` (shared by `products.ts` + `advertising.ts`; self-animates via rAF + explicit `window.scrollTo(0,y)` every frame). `html` keeps `scrollbar-gutter:stable` + `overflow-x:hidden` in `reset.css`. **The seller dashboard stacks THREE sticky layers** a JS scroll target must clear: fixed site header (`--site-header-h`) + sticky tab strip (`--dash-tabs-h`) + the sticky `.dash-panel-head` (no CSS var — measure it live). Missing the panel-head layer lands the target hidden beneath it.

## Hard rules
- **TypeScript everywhere** — no `.js` in `src/`, no `any`.
- **Tailwind v4 only** — no new CSS files or `<style>` blocks; convert existing CSS **on contact only** (no dedicated conversion sessions — decided 2026-07-15 after 10 rounds showed weak byte-savings ROI; the real payoff is less legacy-CSS context to carry, which only justifies touching a file when a real feature already touches it). **What "on contact" does and does not cover (sharpened 2026-07-28 — the rule read as universal, so it was silently skipped whenever it didn't apply and then skipped when it did):** convert a rule you touched when it is a **plain style on an element the component actually renders** — spacing, colour, radius, border, a simple flex/grid box. **Leave as CSS, it is not a failure to convert:** (a) a **descendant selector** whose target the component doesn't own (`.home-shelf .store-card` — moving it onto `StoreCard` would apply it everywhere that component is used); (b) `tokens.css` and any `@theme` / custom-property declaration; (c) `@keyframes`, and `::before`/`::after` carrying real geometry; (d) a value that needs a multi-part `calc()`/`clamp()` over custom properties — escaped into bracket syntax it becomes unreadable, and unreadable beats un-migrated; (e) anything a `:has()`/`[dir=rtl]`/`.is-stuck` state selector drives; (f) **a value another unlayered legacy class on the SAME element also sets** — the utility loses and needs `!`, which is worse than leaving it (hit 2026-07-28: `.store-controls`'s `margin-bottom:1rem` beat a `mb-6` utility on the same element, so the conversion was reverted). **Also read the `main.css` bullet below before converting**: a per-page `<style>` block already gets its own route chunk, so converting it can *increase* the global bundle. When you skip a conversion for one of these reasons, say so in the session summary — that is what stops the rule from rotting again. Never name a custom class the same as a Tailwind utility (e.g. `.grid`) — unlayered legacy CSS beats `@layer utilities` regardless of source order. A `@media` override doesn't gain specificity — a same-specificity unscoped rule later in the file wins regardless of viewport; qualify with an ancestor ID instead of relying on source order. **Remaining legacy CSS** (convert only what you're touching): `pages/dashboard.css` (4 sections: gallery/preview box; products-table core incl. sticky headers; mobile card layout; `.dash-tabs`/`.dash-panel`/`.dash-head`/`.card` which `admin.css` depends on directly — never touch without checking admin panel components first), `pages/store.css` (103 classes, not yet scanned), `seller/dashboard.astro`'s `<style is:global>` (blocked until admin-class-sharing resolved), `buyer/dashboard.astro`'s `<style>`. (The old "stray hex in `StoreAvatar.astro`/`index.astro`" item is done — both are at 0 hexes, verified 2026-07-28.) When converting: keep a class's name in markup as an empty marker (no CSS) if any JS does `querySelector`/`closest` on it — strip only the CSS, never the classname.
- **`main.css` is global — every byte loads on every page.** A legacy `pages/*.css` file may only be moved out of `main.css` into a direct per-page `import` if every one of its classnames is provably unique to that page (checked programmatically, not by eye — short/generic names like `.field`/`.btn`/`.is-loading`/`.hidden` routinely collide across page files and rely on `main.css`'s import order to cascade). `admin.css` was split this way (2026-07-15; admin routes are auth-gated + not indexed, so this also keeps that weight off every public/SEO page); `dashboard.css`/`store.css` were checked and are NOT safe to split — they carry shared-component rules (Header/StoreCard/etc. reused across routes) and override generic classnames from `components/*.css` on purpose. **Gotcha (checkout.astro, 2026-07-15):** a page-owned `<style>` block (even `is:global`) already gets its own per-route CSS chunk from Astro's bundler — `is:global` only disables scoping/hashing, not bundling. Converting such an already-isolated block to Tailwind moves its weight into the one shared Tailwind output (loaded everywhere via `main.css`'s `@import "tailwindcss"`), so it can *increase* the global bundle. Only genuinely cross-page CSS (`dashboard.css`/`store.css`, or a `BaseLayout`-rendered component like `ProductQuickView.astro`) shrinks the global bundle when converted — track this before assuming a conversion is a net byte win.
- **`<Image />` from `astro:assets`** for all platform images.
- **Images optimize themselves — never per-surface, never by reminder (user, 2026-07-28: "I don't want to repeat this instruction; it recurs across the project in a different place every time").** Every image URL goes through `src/lib/cdn.ts` — `cdnSrc(url,w)` (responsive/hero, pair with `cdnSrcSet` + `sizes`), `cdnThumb(url,w,h)` (any fixed-size cell: cart/order/table/search rows — pass 2x the CSS size), `cdnFill` (off-site consumers only). It rewrites Cloudinary uploads **and** routes any other remote host through Cloudinary *fetch* delivery, so a foreign URL is resized + re-formatted + cached like our own. Handing a raw URL to an `<img>` is the bug, not a shortcut: a 1000px original in a 220px tile is ~8x the bytes, and the demo host (`cdn.dummyjson.com`) sends `cache-control: no-store` — nothing on our side can override that, so every refresh re-downloaded the whole page (measured 2026-07-28: homepage 3.88MB → 343KB, 69 tiles). Every `<img>` also declares `loading` + `decoding`; above-the-fold/LCP images get `loading="eager"` + `fetchpriority="high"`. **Never hand-roll lazy-loading** (IntersectionObserver + `data-lazy-src`): an `<img>` with no `src` is invisible to the browser's preload scanner, so nothing downloads until the page's JS module has loaded and run — and the skeleton replays on every refresh even for cached images. Native `loading="lazy"` defers off-screen images without that cost. `tests/image-optimization.test.ts` enforces all of this mechanically over `src/**` — it is the reason the rule can't rot again; fix the markup rather than the allowlist.
- **Design tokens via `tokens.css`** — never hardcode a hex or a corner radius. Colors: `[color:var(--color-X)]`. **Radius = a 3-step scale** (2026-07-27, ~215 sites swept onto it): `--radius-sm` 6px (controls under ~36px — chips, icon buttons, menu items, small thumbs) / `--radius` = `--radius-md` 10px (default — buttons, inputs, cards, panels, dropdowns, tables) / `--radius-lg` 14px (modals, dialogs, drawers, toasts). Declared in `@theme`, **not `:root`** — `--radius-*` is Tailwind v4's own namespace, so in `:root` ours would merely shadow its defaults on source order and `rounded-sm` could silently disagree with a hand-written `var(--radius-sm)`; `--radius-*: initial` drops the rest of the namespace so an off-scale `rounded-xl` doesn't compile at all. Exempt (different intent, not a 4th step): pills/circles (`rounded-full`, 999px, 50%), 2–3px colour swatches, and `lib/email/` (mail clients don't resolve custom properties).
- **No emoji** — inline SVG icons (`aria-hidden="true"`, `currentColor`).
- **Lighthouse 100 target** — semantic HTML, proper alt/width/height, lazy loading.
- **Mobile-first** — 375px viewport, scale up with `sm:`/`md:`/`lg:`.
- **Modular** — UI = display only; DB/API/Cloudinary → `/src/services/` or `/pages/api/`. No file > 200 lines. SRP always.
- **Dropdown design system** — all dropdowns: `background:var(--color-surface)`, `padding:0.3rem` container, items `var(--radius-sm)` + `padding:0.45rem 0.75rem` + hover `var(--color-bg)`, spring `cubic-bezier(0.34,1.56,0.64,1) 0.13s`.
- **Micro-interactions** — `scale(0.97)` button `:active`; image `scale(1.06)` card hover; shadow growth; spring `cubic-bezier(0.34,1.56,0.64,1)`, 100–180ms hover / 220–320ms springs. No border-darkening; every animation needs a reason. `spawnRipple()` clips to its own dedicated inner layer, never the target button directly (clipping the button can swallow a corner badge, e.g. an alert dot, while `overflow:hidden` sticks). **Native browser dialogs are banned site-wide (user, 2026-07-28) — no `confirm()`, `alert()` or `prompt()` anywhere.** Every message the user sees is the site's own UI: a confirmation goes through `ConfirmModal.astro` (`confirm:open` event, title/message/okLabel/workingLabel + `onConfirm`), a notice through `showToast`/`showErrorToast` (`src/lib/toast.ts`) — never hand-build the `toast:show` event. The last 13 (3 confirms + 10 alerts, all in admin/dashboard scripts) were converted 2026-07-28; a `grep -n "alert(\|confirm(\|prompt("` over `src/` should stay empty. **In-flight loading** (delete/save/inline edit): disable the control + show `.dot-pulse` (`utils.css`), not a spinner. `ConfirmModal.onConfirm` may return a `Promise` — dialog stays open (disabled, dots showing) until it resolves. A button whose disabled state is really a brief success confirmation (add-to-cart checkmark) gets `.btn--confirmed` (`buttons.css`). **The `not-allowed` "no-entry" cursor is banned site-wide (user, 2026-07-26) — never use it anywhere.** Disabled controls use `cursor:default` (a global `reset.css` rule enforces this on `:disabled`/`[aria-disabled]`, overriding the UA default); an in-flight busy control uses `cursor:progress` (`.btn--busy`). All resizable `<textarea>`s are `resize:none` (fixed standard box) — also a standing user preference.
- **One shared badge finish** — every chip in a store card's badge row (`.store-card__tags`: StoreDemoBadge, `.sale-chip`, `.store-card__tag`) draws its fill/border/shadow from `.badge-finish` (utilities/utils.css) and differs ONLY by `--badge-hue`. Promoted out of StoreDemoBadge's inline style once it had three consumers; a private copy is how the row's chips drift apart one edit at a time. Geometry must also match (0.68rem/1.5 line-height/pill) or the row's `min-height:22px` starts carrying it by stretch.
- **Design line — decide by it, not by taste.** Minimalist, timeless, category-agnostic, no gimmicks. Four tests, and a treatment has to pass all four: (1) **Is it already in the system?** Prefer a token, an existing component recipe, or an existing gesture over anything invented for one component — a bespoke treatment reads as imposed even when each individual value is defensible. (2) **Would it date?** Travelling gloss/shine, stacked bevels, decorative diagonals and oversized background glyphs read as a specific year; a surface, a rule and type do not. (3) **Does it suit every category?** The same page must look right for a tool shop, a fashion boutique and a grocery — a coloured frame or a seasonal flourish fails this while a plain surface passes. (4) **Is the colour already spoken for?** Each accent has ONE job (see `--color-sale`: the sale price, badge and banner share one green "so a shopper learns the mark once"); spending it on decoration dilutes the signal it exists to carry. Restraint here is the design, not an absence of it — corollary of the tactile-depth rule below, which likewise ends "not neumorphism, not brutalist neon borders". The store-wide sale strip (`.store-sale`, utilities/utils.css) is the worked example: eight bespoke treatments were tried and discarded before it became `.card` plus a green number, and its comment lists each failure so the path is not re-walked.
- **"Tactile depth" design language** (site-wide since 2026-07-07: product/home/store/dashboard/checkout/cart/PQV). **Lone/hero surfaces** (single image wrap, detail card): `border:1.5px` + `--shadow-card` → `--shadow-card-hover` on hover. **Secondary/repeated cards** (grid/list items): lighter `border:1px` + `--shadow-xs` → `--shadow-card-hover` on hover — `shadow-card` at rest reads heavy multiplied across a grid. **Full-width list rows** (order card, table row): skip shadow-hover, use a `border-color` tint — the shadow's blur/spread is calibrated for spaced grid cards, reads excessive flush against neighbors. Qty steppers always flat (`border:1px`, no inset shadow/fill — a filled pill read as disabled). No `translateY` hover-lift on a card whose image already hover-zooms — **exception:** homepage product cards keep `translateY(-5px)` deliberately as a felt differentiator from in-store product cards. Image containers holding a possibly-transparent (bg-removed) photo must use `background:var(--color-surface)` (white), never `--color-bg`/none, plus a `border-bottom` separating image from body when both are white. Tokens in `tokens.css`. Restrained on purpose — not neumorphism, not brutalist neon borders.
- **Backward-compatible API/DB — always additive (zero-downtime deploy rule).** During a production deploy the old and new versions run against the same DB for a few seconds, so every `/api/*` response shape and every DB schema change must keep the *previous* version working: only add fields/columns, never remove or repurpose one the deployed code still reads. A real breaking change is two deploys — first stop reading the field, then (next deploy) remove it; a breaking API needs `/api/v2/`, not an edit in place. This is the same discipline as Data models' "add fields, never remove without discussion", extended to responses + migrations. Full deploy-safety context: `GO_LIVE_CHECKLIST.md` §7.
