## What we're building
Multi-vendor internet mall for the Israeli market. Sellers open stores; shoppers discover across them. Two independent SEO surfaces: platform (discovery) + each store (standalone feel).

**Mission:** Hebrew digital mall, separate checkout per seller. **Pricing (decided 2026-07-21, model-design only — no code yet; see memory `project_business_model_pricing`):** clean subscription **tiers** = fixed monthly fee + per-sale commission, where a higher tier lowers the commission (Starter 99₪/mo + ~10–12% … Enterprise high + ~3–4%); both charged additively (not offset). **Advertising is a fully separate component** — pay-per-actual-spend via Authorize/Capture (+ a disclosed platform margin), never offset against subscription/commission. **Free trial (14–30d) with card at signup.** (Supersedes the old "no fixed fees / success-based only" line.) **Sellers = registered businesses only** (עצמאים/עוסק פטור/מורשה, small-medium biz) — not private individuals; matches the split-payment provider's sub-merchant requirement and differentiates from Israeli P2P marketplaces (My Product, Yad2), which serve private sellers via manual escrow, not a branded storefront + shipping + marketing. **Fixed platform template only** — no per-seller site/theme design tooling, ever (deliberate scope boundary). Not competing with Wix/Shopify on design freedom — target seller wants zero design decisions and speed. **Zero-touch self-service** — platform owner has no manual, ongoing involvement with sellers/buyers; every flow (registration, upload, fulfillment, messaging, disputes) defaults to fully automated, never owner approval — a scale requirement (see Hard rules → Scalability). Any new feature involving admin/manual gatekeeping must default to an automated equivalent instead.

### Israeli market — hard constraints
- **Payments:** Split-payment via Israeli marketplace-capable processor — SUMIT or תקבול (Takbull), final pick pending (see Payment architecture). Never Stripe.
- **Shipping:** Sendit / Israel Post / iPost only.

### Payment architecture — decided (2026-07-06)
**Split payment via the payment processor.** Platform never holds seller funds — each seller has a sub-merchant account with the processor, which splits payment automatically at checkout (seller's share → seller, commission → platform). Reason: platform holding + manually disbursing seller money would be a regulated PSP service in Israel; split payment keeps the platform a pure software/marketplace layer.
- Candidates: **SUMIT** and **תקבול (Takbull)** explicitly market a marketplace/split model — final pick pending direct confirmation of terms. Cardcom/Payme/Tranzila/PayPlus/Meshulam are common gateways but sub-merchant split support unconfirmed.
- No manual payout queue — processor pays sellers directly, so admin never marks payouts "paid". `SellerBalance`/admin dashboard is a **reporting** view (totalEarned per seller) only.
- Commission % deducted at processor/order level (`store.config.ts` → `checkout.commissionPercent`).

### Checkout — decided
Guest checkout only. Buyer: name, email, phone, address. No buyer registration/login/dashboard.

## Architecture
- **Stack:** Astro 7 + Node adapter, TypeScript, Tailwind v4, self-hosted Heebo, `tokens.css` color system. Dev toolbar disabled. Astro 7's compiler rejects an HTML comment as the first child right after `{expr && (` — place comments above the expression, not inside it.
- **Fonts:** hand-written `@font-face` in `main.css` (not `@fontsource`'s per-weight CSS — trims unused subsets, still reuses its font files). `font-display:optional`, not `swap`. **All 10 weight×script combos (400-800 × hebrew/latin) preloaded in `BaseLayout.astro` (2026-07-16)** — preloading only weight 800 left every other combo to fallback-then-swap on first layout (real, measured layout-shift).
- **View Transitions — investigated, not adopted (2026-07-16):** `ClientRouter` is opt-out-per-link, not opt-in — enabling it soft-navigates the whole site by default (full `DOMContentLoaded`→`astro:page-load` audit either way). The JS-free native `@view-transition` CSS alternative was tried and reverted same session: its 4s renderable timeout was blown by a render-blocking font `<link>` (now fixed, see Fonts), stalling then snapping. Never re-verified since — don't assume it's safe to retry without a fresh check.
- **Split:** content pages = static, seller/admin/api = SSR.
- **Header:** `position:fixed` + `body{padding-top:3.3rem}` — never sticky. Desktop search sits flush after the logo (not centered) — confirmed 2026-07-09, don't re-center without asking. No entrance/pop-in animation on anything in `BaseLayout`/`Header.astro` — an MPA recreates those elements on every navigation, so the animation replays every time (removed one 2026-07-16 for this). Header row always renders `class="container"` (never the old `container between flex`) — every page passes `storeMode` (seller register/login/dashboard included) so row layout is one mechanism everywhere; row carries `min-height:2rem` (search input height) so icons center identically with or without a search bar. `.user-btn`/`.user-menu` pre-declared `position:relative`/`display:flex` rather than left to `spawnRipple()`'s static→relative promotion — the alert dot nests *inside* `.user-btn`, so a ripple-triggered position change on first click would've silently changed the dot's containing block (fixed 2026-07-16).
- **Data:** `data/*.json` dev-only; pure DB adapter functions, swap-ready for SQLite/Postgres.
- **Scroll:** never `window.scrollTo({top,behavior:'smooth'})` for a JS-computed target on this RTL site — native smooth-scroll visibly drifts `scrollX` off 0 mid-animation (off-thread, un-correctable via rAF). Use `animateScrollTo()` in `products.ts` (self-animates via rAF + explicit `window.scrollTo(0,y)` every frame). `html` keeps `scrollbar-gutter:stable` + `overflow-x:hidden` in `reset.css`.

## Hard rules
- **TypeScript everywhere** — no `.js` in `src/`, no `any`.
- **Tailwind v4 only** — no new CSS files or `<style>` blocks; convert existing CSS **on contact only** (no dedicated conversion sessions — decided 2026-07-15 after 10 rounds showed weak byte-savings ROI; the real payoff is less legacy-CSS context to carry, which only justifies touching a file when a real feature already touches it). Never name a custom class the same as a Tailwind utility (e.g. `.grid`) — unlayered legacy CSS beats `@layer utilities` regardless of source order. A `@media` override doesn't gain specificity — a same-specificity unscoped rule later in the file wins regardless of viewport; qualify with an ancestor ID instead of relying on source order. **Remaining legacy CSS** (convert only what you're touching): `pages/dashboard.css` (4 sections: gallery/preview box; products-table core incl. sticky headers; mobile card layout; `.dash-tabs`/`.dash-panel`/`.dash-head`/`.card` which `admin.css` depends on directly — never touch without checking admin panel components first), `pages/store.css` (103 classes, not yet scanned), `seller/dashboard.astro`'s `<style is:global>` (blocked until admin-class-sharing resolved), `buyer/dashboard.astro`'s `<style>`, stray hex in `StoreAvatar.astro`/`index.astro`. When converting: keep a class's name in markup as an empty marker (no CSS) if any JS does `querySelector`/`closest` on it — strip only the CSS, never the classname.
- **`main.css` is global — every byte loads on every page.** A legacy `pages/*.css` file may only be moved out of `main.css` into a direct per-page `import` if every one of its classnames is provably unique to that page (checked programmatically, not by eye — short/generic names like `.field`/`.btn`/`.is-loading`/`.hidden` routinely collide across page files and rely on `main.css`'s import order to cascade). `admin.css` was split this way (2026-07-15; admin routes are auth-gated + not indexed, so this also keeps that weight off every public/SEO page); `dashboard.css`/`store.css` were checked and are NOT safe to split — they carry shared-component rules (Header/StoreCard/etc. reused across routes) and override generic classnames from `components/*.css` on purpose. **Gotcha (checkout.astro, 2026-07-15):** a page-owned `<style>` block (even `is:global`) already gets its own per-route CSS chunk from Astro's bundler — `is:global` only disables scoping/hashing, not bundling. Converting such an already-isolated block to Tailwind moves its weight into the one shared Tailwind output (loaded everywhere via `main.css`'s `@import "tailwindcss"`), so it can *increase* the global bundle. Only genuinely cross-page CSS (`dashboard.css`/`store.css`, or a `BaseLayout`-rendered component like `ProductQuickView.astro`) shrinks the global bundle when converted — track this before assuming a conversion is a net byte win.
- **`<Image />` from `astro:assets`** for all platform images.
- **Colors via `tokens.css`** — never hardcode hex. Use `[color:var(--color-X)]`.
- **No emoji** — inline SVG icons (`aria-hidden="true"`, `currentColor`).
- **Lighthouse 100 target** — semantic HTML, proper alt/width/height, lazy loading.
- **Mobile-first** — 375px viewport, scale up with `sm:`/`md:`/`lg:`.
- **Modular** — UI = display only; DB/API/Cloudinary → `/src/services/` or `/pages/api/`. No file > 200 lines. SRP always.
- **Dropdown design system** — all dropdowns: `background:var(--color-surface)`, `padding:0.3rem` container, items `border-radius:4px` + `padding:0.45rem 0.75rem` + hover `var(--color-bg)`, spring `cubic-bezier(0.34,1.56,0.64,1) 0.13s`.
- **Micro-interactions** — `scale(0.97)` button `:active`; image `scale(1.06)` card hover; shadow growth; spring `cubic-bezier(0.34,1.56,0.64,1)`, 100–180ms hover / 220–320ms springs. No border-darkening; every animation needs a reason. `spawnRipple()` clips to its own dedicated inner layer, never the target button directly (clipping the button can swallow a corner badge, e.g. an alert dot, while `overflow:hidden` sticks). **In-flight loading** (delete/save/inline edit): disable the control + show `.dot-pulse` (`utils.css`), not a spinner. `ConfirmModal.onConfirm` may return a `Promise` — dialog stays open (disabled, dots showing) until it resolves. A button whose disabled state is really a brief success confirmation (add-to-cart checkmark) gets `.btn--confirmed` (`buttons.css`) instead of the sitewide `cursor:not-allowed`.
- **"Tactile depth" design language** (site-wide since 2026-07-07: product/home/store/dashboard/checkout/cart/PQV). **Lone/hero surfaces** (single image wrap, detail card): `border:1.5px` + `--shadow-card` → `--shadow-card-hover` on hover. **Secondary/repeated cards** (grid/list items): lighter `border:1px` + `--shadow-xs` → `--shadow-card-hover` on hover — `shadow-card` at rest reads heavy multiplied across a grid. **Full-width list rows** (order card, table row): skip shadow-hover, use a `border-color` tint — the shadow's blur/spread is calibrated for spaced grid cards, reads excessive flush against neighbors. Qty steppers always flat (`border:1px`, no inset shadow/fill — a filled pill read as disabled). No `translateY` hover-lift on a card whose image already hover-zooms — **exception:** homepage product cards keep `translateY(-5px)` deliberately as a felt differentiator from in-store product cards. Image containers holding a possibly-transparent (bg-removed) photo must use `background:var(--color-surface)` (white), never `--color-bg`/none, plus a `border-bottom` separating image from body when both are white. Tokens in `tokens.css`. Restrained on purpose — not neumorphism, not brutalist neon borders.
- **Backward-compatible API/DB — always additive (zero-downtime deploy rule).** During a production deploy the old and new versions run against the same DB for a few seconds, so every `/api/*` response shape and every DB schema change must keep the *previous* version working: only add fields/columns, never remove or repurpose one the deployed code still reads. A real breaking change is two deploys — first stop reading the field, then (next deploy) remove it; a breaking API needs `/api/v2/`, not an edit in place. This is the same discipline as Data models' "add fields, never remove without discussion", extended to responses + migrations. Full deploy-safety context: `GO_LIVE_CHECKLIST.md` §7.
- **Scalability** — stateless API routes; no shared write state. Ask: breaks at 1000 sellers + 10,000 buyers? **Known JSON-file cost to revisit at DB migration:** header's SSR-computed indicators (notif badge, avatar alert dot via `sellerHasAnyAlert`) run on every page a logged-in seller loads and do a full file-read+parse+filter per store/thread, no cache/index — negligible today, becomes an indexed query at real-DB time (same function signatures, only internals change).
- **Inventory integrity** — atomic `decrementStock(productId,qty):Promise<boolean>`. JSON: async mutex (`src/lib/mutex.ts`). DB: `BEGIN TRANSACTION; UPDATE ... WHERE stock >= qty`. Payment webhooks: idempotency check on `paymentRef`.
- **Testing** — `tsc` after every change, **and `npx astro check` whenever a `.astro` file's `<script>`/frontmatter changed** — plain `tsc --noEmit` can't parse `.astro` syntax and silently skips those files (`@astrojs/check` installed to catch this). Real TS control-flow gotcha: a `let` reassigned inside `.forEach`, then read via `if(x)`/`x?.` right after the loop, narrows to `never` — rewrite as `filter().map().filter(guard)`. Vitest set up (`tests/`, default `node` env, per-file `// @vitest-environment jsdom` only where DOM/localStorage is touched, `npm test`). **Standing policy: any change that moves money or decrements stock needs a Vitest test in the same change** — not "extra scope"; applies to `orders.ts`, `cart.ts`, `/api/checkout`, `store-products(-bulk).ts`, `/api/store-product/bulk`, and any future money/stock code.
