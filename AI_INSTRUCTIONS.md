## What we're building
Multi-vendor internet mall for the Israeli market. Sellers open stores; shoppers discover across them. Two independent SEO surfaces: platform (discovery) + each store (standalone feel).

**Mission:** Hebrew digital mall, no fixed fees (success-based only), separate checkout per seller. **Sellers = registered businesses only** (עצמאים/עוסק פטור/מורשה, small-medium biz) — not private individuals; matches the split-payment provider's sub-merchant requirement and differentiates from Israeli P2P marketplaces (My Product, Yad2), which serve private sellers via manual escrow, not a branded storefront + shipping + marketing. **Fixed platform template only** — no per-seller site/theme design tooling, ever (deliberate scope boundary). Not competing with Wix/Shopify on design freedom — target seller wants zero design decisions and speed. **Zero-touch self-service** — platform owner has no manual, ongoing involvement with sellers/buyers; every seller/buyer flow (registration, upload, fulfillment, messaging, disputes) defaults to fully automated/self-service, never owner approval — a scale requirement (see Hard rules → Scalability). Any new feature involving admin/manual gatekeeping must default to an automated equivalent instead.

### Every seller gets out of the box
1. **Store** — product pages, SEO, platform discovery
2. **Shipping** — integrated Israeli carrier, per-store config, tracking
3. **Marketing** — GTM + Meta Pixel on every page; dataLayer feeds campaigns; seller picks budget only

### Israeli market — hard constraints
- **Payments:** Split-payment via Israeli marketplace-capable processor — SUMIT or תקבול (Takbull), final pick pending (see "Payment architecture" below). Never Stripe.
- **Shipping:** Sendit / Israel Post / iPost only.
- **Currency:** ILS (₪) always.
- **Language:** Hebrew-first, RTL.

### Payment architecture — decided (2026-07-06)
**Split payment via the payment processor.** Platform never holds seller funds — each seller has a sub-merchant/business account with the processor, which splits payment automatically at checkout (seller's share → seller, commission → platform). Reason: platform holding + manually disbursing seller money would be a regulated PSP service in Israel; split payment keeps the platform a pure software/marketplace layer.
- Candidates: **SUMIT** and **תקבול (Takbull)** explicitly market a marketplace/split-payment model — final pick pending direct confirmation of terms. Cardcom/Payme/Tranzila/PayPlus/Meshulam are common gateways but sub-merchant split support is unconfirmed.
- No manual payout queue — processor pays sellers directly, so admin never marks payouts "paid". `SellerBalance`/admin dashboard is a **reporting** view (totalEarned per seller) only.
- Commission % deducted at processor/order level (`store.config.ts` → `checkout.commissionPercent`).

### Checkout — decided
Guest checkout only. Buyer: name, email, phone, address. No buyer registration/login/dashboard.

### Data models — canonical (add fields, never remove without discussion)
```
Order { id, buyerName, buyerEmail, buyerPhone, buyerAddress,
  items:[{productId,productName,storeSlug,storeName,price,qty,image}],
  shippingAmount, totalAmount, paymentRef, paymentStatus:'pending'|'paid'|'failed',
  shippingStatus:'pending'|'processing'|'shipped'|'delivered', trackingNumber?,
  createdAt, updatedAt, buyerId? }
SellerBalance { sellerId, storeId, totalEarned }  // reporting only — split payment means processor pays seller directly, no totalPaidOut/manual payout
Store (add): shipping:{flatRate,freeAbove,processingDays}, contactEmail
StoreProduct (add): weight? (grams)
```

### Proactive obligations — always
- **dataLayer events** — page_view, view_item, add_to_cart, begin_checkout, purchase → `window.dataLayer` + `window.fbq`. Use `src/lib/tracking.ts`.
- **SEO** — every public page: unique title, description, JSON-LD, canonical via `BaseLayout → Seo.astro`.
- **Shipping** — always read from store settings, never hardcode.

## Architecture
- **Stack:** Astro 7 + Node adapter, TypeScript, Tailwind v4, self-hosted Heebo, `tokens.css` color system. Dev toolbar disabled. Astro 7's compiler rejects an HTML comment as the first child right after `{expr && (` — place comments above the expression, not inside it.
- **Fonts:** hand-written `@font-face` in `main.css` (not `@fontsource`'s own per-weight CSS — trims unused subsets, still reuses its font files). `font-display:optional`, not `swap`. **All 10 weight×script combos (400-800 × hebrew/latin) preloaded in `BaseLayout.astro` (2026-07-16)** — preloading only weight 800 left every other combo free to fallback-then-swap on first layout (real, measured layout-shift, not just cold-visit).
- **View Transitions — investigated, not adopted (2026-07-16):** `ClientRouter` is opt-out-per-link, not opt-in — enabling it soft-navigates the whole site by default (full `DOMContentLoaded`→`astro:page-load` audit either way). The JS-free native `@view-transition` CSS alternative was tried and reverted same session: its 4s renderable timeout was blown by a render-blocking font `<link>` (now fixed, see Fonts), stalling then snapping. Never re-verified since — don't assume it's safe to retry without a fresh check.
- **Split:** content pages = static, seller/admin/api = SSR.
- **Header:** `position:fixed` + `body{padding-top:3.3rem}` — never sticky. Desktop search sits flush after the logo (not centered) — confirmed preference 2026-07-09, don't re-center without asking. No entrance/pop-in animation on anything living in `BaseLayout`/`Header.astro` — an MPA recreates those elements on every navigation, so the animation would replay every time, not just once (removed one 2026-07-16 for exactly this). Header row always renders `class="container"` (never the old `container between flex`) — every page passes `storeMode` (seller register/login/dashboard now included) so the row layout is one mechanism everywhere; the row also carries `min-height:2rem` (the search input's height) so icons center identically whether or not that page renders a search bar. `.user-btn`/`.user-menu` are pre-declared `position:relative`/`display:flex` rather than left to `spawnRipple()`'s own static→relative promotion — the alert dot is nested *inside* `.user-btn`, so a ripple-triggered position change on first click would've silently changed the dot's containing block (fixed 2026-07-16).
- **Data:** `data/*.json` dev-only; pure DB adapter functions, swap-ready for SQLite/Postgres.
- **Scroll:** never use `window.scrollTo({top,behavior:'smooth'})` for a JS-computed target on this RTL site — native smooth-scroll visibly drifts `scrollX` off 0 mid-animation (runs off-thread, un-correctable via rAF). Use `animateScrollTo()` in `products.ts` (self-animates via rAF + explicit `window.scrollTo(0,y)` every frame). `html` also keeps `scrollbar-gutter:stable` + `overflow-x:hidden` in `reset.css`.

## Hard rules
- **TypeScript everywhere** — no `.js` in `src/`, no `any`.
- **Tailwind v4 only** — no new CSS files or `<style>` blocks; convert existing CSS **on contact only** (no dedicated conversion sessions — decided 2026-07-15 after 10 rounds showed weak byte-savings ROI; the real payoff is less legacy-CSS context to carry, which only justifies touching a file when a real feature already touches it). Never name a custom class the same as a Tailwind utility (e.g. `.grid`) — unlayered legacy CSS beats `@layer utilities` regardless of source order. A `@media` override doesn't gain specificity — a same-specificity unscoped rule later in the file wins regardless of viewport; qualify with an ancestor ID instead of relying on source order. **Remaining legacy CSS surface** (convert only what you're already touching): `src/styles/pages/dashboard.css` (4 sections left — gallery/preview box, products-table core incl. sticky headers, mobile card layout, and `.dash-tabs`/`.dash-panel`/`.dash-head`/`.card` which `admin.css` depends on directly and must never be touched without checking admin panel components first), `src/styles/pages/store.css` (103 classes, not yet scanned), `seller/dashboard.astro`'s `<style is:global>` (blocked until admin-class-sharing is resolved), `buyer/dashboard.astro`'s own `<style>`, stray hex in `StoreAvatar.astro`/`index.astro`. When converting: keep a class's name in markup as an empty marker (no CSS) if any JS does `querySelector`/`closest` on it — strip only the CSS, never the classname itself.
- **`main.css` is global — every byte loads on every page.** A legacy `src/styles/pages/*.css` file may only be moved out of `main.css` into a direct `import '…css'` on its own page file if every one of its classnames is provably unique to that page (checked programmatically, not by eye — short/generic names like `.field`/`.btn`/`.is-loading`/`.hidden` routinely collide across page files and rely today on `main.css`'s import order to cascade correctly). `admin.css` was split out this way (2026-07-15, admin routes are auth-gated + not indexed, so this also keeps that weight off every public/SEO page); `dashboard.css`/`store.css` were checked and are NOT safe to split — they carry shared-component rules (Header/StoreCard/etc. reused across many routes) and override generic classnames from `components/*.css` on purpose. **Gotcha found converting `checkout.astro` (2026-07-15):** a page-owned `<style>` block (even `is:global`) already gets its own per-route CSS chunk from Astro's bundler regardless of the `is:global` attribute — that keyword only disables scoping/hashing, not bundling. Converting such an already-isolated block to Tailwind utilities moves its weight into the one shared Tailwind output (loaded on every page via `main.css`'s `@import "tailwindcss"`), so it can *increase* the global bundle even though the source `<style>` block disappears. Only genuinely cross-page CSS (`dashboard.css`/`store.css`, already `@import`ed into `main.css`, or a component like `ProductQuickView.astro` that's rendered from `BaseLayout` on every page) shrinks the global bundle when converted — track that distinction before assuming a Tailwind conversion is a net byte win.
- **`<Image />` from `astro:assets`** for all platform images.
- **Colors via `tokens.css`** — never hardcode hex. Use `[color:var(--color-X)]`.
- **No emoji** — inline SVG icons (`aria-hidden="true"`, `currentColor`).
- **Lighthouse 100 target** — semantic HTML, proper alt/width/height, lazy loading.
- **Mobile-first** — 375px viewport, scale up with `sm:`/`md:`/`lg:`.
- **Modular** — UI = display only; DB/API/Cloudinary → `/src/services/` or `/pages/api/`. No file > 200 lines. SRP always.
- **Dropdown design system** — all dropdowns: `background:var(--color-surface)`, `padding:0.3rem` container, items `border-radius:4px` + `padding:0.45rem 0.75rem` + hover `var(--color-bg)`, spring `cubic-bezier(0.34,1.56,0.64,1) 0.13s`.
- **Micro-interactions** — `scale(0.97)` button `:active`; image `scale(1.06)` card hover; shadow growth; spring `cubic-bezier(0.34,1.56,0.64,1)`, 100–180ms hover / 220–320ms springs. No border-darkening; every animation needs a reason. `spawnRipple()` clips to its own dedicated inner layer, never the target button directly (clipping the button itself can swallow a corner badge, e.g. an alert dot, for as long as `overflow:hidden` sticks). **In-flight loading** (delete/save/inline edit): disable the control + show `.dot-pulse` (`utils.css`), not a spinner. `ConfirmModal.onConfirm` may return a `Promise` — dialog stays open (disabled, dots showing) until it resolves. A button whose disabled state is really a brief success confirmation (e.g. add-to-cart checkmark) gets `.btn--confirmed` (`buttons.css`) instead of the sitewide `cursor:not-allowed`.
- **"Tactile depth" design language** (site-wide since 2026-07-07: product/home/store/dashboard/checkout/cart/PQV). **Lone/hero surfaces** (single image wrap, detail card): `border:1.5px` + `--shadow-card` → `--shadow-card-hover` on hover. **Secondary/repeated cards** (grid/list items): lighter `border:1px` + `--shadow-xs` → `--shadow-card-hover` on hover — `shadow-card` at rest reads heavy once multiplied across a grid. **Full-width list rows** (order card, table row): skip shadow-hover, use a `border-color` tint instead — the shadow's blur/spread is calibrated for spaced grid cards and reads excessive flush against neighbors. Qty steppers are always flat (`border:1px`, no inset shadow/fill — a filled pill read as disabled). No `translateY` hover-lift on a card whose image already hover-zooms — **exception:** homepage product cards keep `translateY(-5px)` deliberately as a felt differentiator from in-store product cards. Image containers holding a possibly-transparent (bg-removed) photo must use `background:var(--color-surface)` (white), never `--color-bg`/none, plus a `border-bottom` separating image from body when both are white. Tokens in `tokens.css`. Restrained on purpose — not neumorphism, not brutalist neon borders.
- **Scalability** — stateless API routes; no shared write state. Ask: breaks at 1000 sellers + 10,000 buyers? **Known JSON-file cost to revisit at DB migration:** header's SSR-computed indicators (notif badge, avatar alert dot via `sellerHasAnyAlert`) now run on every page a logged-in seller loads and do a full file-read+parse+filter per store/thread, no cache/index — negligible today, becomes an indexed query at real-DB time (same function signatures, only internals change).
- **Inventory integrity** — atomic `decrementStock(productId,qty):Promise<boolean>`. JSON: async mutex (`src/lib/mutex.ts`). DB: `BEGIN TRANSACTION; UPDATE ... WHERE stock >= qty`. Payment webhooks: idempotency check on `paymentRef`.
- **Testing** — `tsc` after every change, **and `npx astro check` whenever a `.astro` file's `<script>`/frontmatter changed** — plain `tsc --noEmit` can't parse `.astro` syntax and silently skips those files entirely (`@astrojs/check` installed as devDependency to catch this). Known `astro check` false-positives to leave alone: (1) a `const` declared right before `Astro.redirect(...)` inside an `if`/`else if` chain gets wrongly flagged `ts(6133)` "never read" — verify with `grep` before "fixing" (deleting it breaks the redirect); (2) "Unreachable code" on a `<script is:inline>` nested inside a conditionally-rendered branch — real, runs fine (`is:inline` is injected raw). Real TS control-flow gotcha: a `let` reassigned inside `.forEach`, then read via `if(x)`/`x?.` right after the loop, narrows to `never` — rewrite as `filter().map().filter(guard)` instead of manual `let`+closure mutation. Vitest set up (`tests/`, default `node` env, per-file `// @vitest-environment jsdom` only where DOM/localStorage is touched, `npm test`) — see Project structure for the current test file list/coverage. **Standing policy: any change that moves money or decrements stock needs a Vitest test in the same change** — not "extra scope"; applies to `orders.ts`, `cart.ts`, `/api/checkout`, `store-products(-bulk).ts`, `/api/store-product/bulk`, and extends to any future money/stock code. Run `npm test` alongside `tsc` after every such change. Playwright is installed (chromium) but reserved for money/inventory/multi-surface bugs, or a UI/interaction claim that can't be verified by reasoning alone — one-off repro scripts, not a committed suite; not for routine changes. **Locating a `.astro` compile error with no file/line in the dev overlay or `astro check` output:** run `npx astro build` — its `[CompilerError]` output includes a `Location:` with exact file:line, unlike the dev server's/check's own stack trace (burned a full session once — don't hand-write an AST-diffing script to binary-search it).
- **Security review gate** — before closing any session whose diff touched money/auth/inventory/cart/checkout code (`orders.ts`, `seller-*`, `cart.ts`, `user-carts.ts`, `checkout.*`, `/api/checkout`, `/api/payment/*`, `/api/auth/*`), run `/code-review` (free tier, not `ultra`) on the diff before reporting done. `/code-review ultra` is user-triggered only, billed — never launch proactively.
- **Production monitoring — future waypoint, not yet built.** Error/log monitoring will live in the seller's own future admin dashboard (see `CURRENT_TASK.md`) rather than a separate tool — flagged early so the dashboard's design leaves room for it.
- **Product reviews — future waypoint, not yet built.** No review/rating feature exists today. When built, buyer-submitted review text must run through the same spam/keyword-stuffing filter already used for seller product/category content — another free-text UGC surface needing the same automatic gate, not a manual moderation queue.
- **Self-healing errors — future waypoint, not yet built (2026-07-15).** Auto-retry (with backoff) for genuinely transient, idempotent failures, auto-marking those log entries "resolved" so the Alerts tab only surfaces things that actually need a human — fits the zero-touch philosophy. Deliberately not built now: today's errors are almost all logic/data bugs (not retryable) or a `data/*.json` write collision that a real DB's own transactions/row-locks make moot — building JSON-specific retry now is throwaway work. Build this once there's a real external call to retry against (split-payment webhook, Cloudinary, future SendGrid/Sendit) or once the DB migration happens (retry on deadlock/dropped-connection instead). **Never retry a non-idempotent operation** (e.g. checkout) blindly — risks double-charging or double-decrementing stock.
- **Accessibility (WCAG 2.1 AA)** — skip link, focus traps on modals, Escape closes overlays, ARIA labels/roles/`aria-expanded`/`aria-live`, visible labels, 4.5:1 contrast, never color-only state.
- **SEO** — `BaseLayout → Seo.astro` always. JSON-LD Product on product pages, Store/LocalBusiness on store pages. Unique title+description per page.
- **i18n** — all strings via `getT(lang)`. Hebrew-first, RTL. Server-side `lang` conditionals for icon placement.
- **Ads — two-tier model (decided 2026-07-06, budget shape decided 2026-07-16):** (1) **Baseline**, platform-funded — every product/store, by default, in a platform-wide feed powering Google Performance Max / Meta Advantage+ Catalog. **Funded by a fixed one-time lifetime budget decided in advance, not a recurring/ongoing subsidy** — set the campaign to a lifetime budget (native setting in both Google Ads and Meta Ads Manager, no custom code needed) rather than a daily budget, so spend auto-stops once the cap is reached instead of renewing every month by default; extending it after is a deliberate decision, not automatic. Needs a bulk feed endpoint (Merchant Center + Meta Catalog) exporting all `StoreProduct`s — not built; today only per-page OG `product:price:*` tags exist (`Seo.astro`). (2) **Boost**, seller-funded — extra pay → more spend on their products; a boost = a **separate dedicated campaign** per store/product (`adCampaigns`, via Google Ads/Meta Marketing API, billed through the split-payment provider) since catalog campaigns can't weight one product inside a shared campaign. Either tier: sellers never touch targeting/creative, budget/duration only. One GTM + one Meta Pixel account for the whole platform (not per-seller) — what makes tier 1 possible with zero seller opt-in. `dataLayer` provides `store_id`, `ecommerce.items`.
- File content in English. Chat in Hebrew.

- **Content moderation / spam prevention:** `spam-filter.ts` — two automatic checks (no manual queue): word-boundary blocklist (not substring — avoids false positives like "XXX-Large") and keyword-stuffing detection (word repeats ≥8 times AND ≥30% of significant words). Admin-only store/product block is the one deliberately manual gate. Every public surface must gate through `isStoreVisible`/`isProductVisible`/etc., never an inline `!x.blocked` filter — a review pass once found 3 surfaces that had forgotten it. **Blocking always notifies the seller** — the seller's reply is the appeal channel.
- **Admin↔seller messaging:** `admin-messages.ts` — flat one-conversation-per-seller (not subject-threaded like buyer↔seller `messages.ts` — admin only ever has one relationship per seller). Seller side: **no separate tab** — the admin thread renders as a pinned "הודעות מערכת" row inside the seller's regular messages tab, using that tab's existing UI. Both sides poll 15s.
- **Operational error logging:** `middleware.ts` logs to `data/error-log.json` (capped 500) only on a genuinely thrown/uncaught exception — deliberately not any route returning `>=500` (an intentional 503 would otherwise be a content-free false-positive). Client-side `error-reporter.ts` posts to unauthenticated `/api/log-client-error` into the same log. **Identity enrichment:** `ErrorLogEntry` carries `storeSlug`/`actorRole`/`actorLabel`/`resolutionHint` so an Alerts row shows who an error happened to; `resolveErrorContext()` wraps its own body in try/catch (must never throw — it runs inside the caller's own catch block, before `logError`'s internal one starts). `route` on the client-report endpoint is unauthenticated client input — spoofable, accepted as low-impact since this is reporting-only. **Manual triage + responsive fix (2026-07-16):** `ErrorLogEntry.resolved?:boolean` — admin toggles a row "handled" (reversible, optimistic). Alerts is a real `<table>` (`table-layout:fixed`+`<colgroup>`) down to 640px, then a stacked card — content-sized columns broke at almost every width before fixed widths. Gotcha: an icon-only button needs its own explicit `flex-shrink:0` even if siblings have it. Gotcha: a per-column `<th>` `text-align` override needs `.class`+type-selector specificity to beat `.admin-table th{text-align:start}`.
