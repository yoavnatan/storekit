After every code step: run TypeScript type checks (`npx tsc --noEmit`) and check terminal logs.

**ESLint + SonarJS added 2026-07-29** — `npm run lint` (config: `eslint.config.js`, plugins `eslint-plugin-sonarjs` + `eslint-plugin-astro`). Run it alongside tsc after a step that changed `.ts`/`.astro` logic; skip it for pure CSS/text edits. It is deliberately tuned narrow (style-only Sonar rules off, complexity as warnings) so the output stays readable — if a rule turns into noise, turn it off in the config rather than learning to ignore the run. The user also installed the "SonarQube for IDE" extension in VSCode; that shows the same rule family in the editor but reads its own defaults, not `eslint.config.js`, so the two lists won't match exactly. `npm run lint` reports **only what the change introduced**, measured against `.eslint-baseline.json` — a frozen record of the pre-existing backlog (106 errors / 43 files, plus 41 warnings that gate nothing), so clean output is the pass condition and the backlog can never block. `lint:all` = whole picture for a cleanup session; `lint:prune` drops suppressions once cleared. **Never run `lint:baseline` to silence a new error** — that is the one move that makes the gate meaningless. Blocking gate is CI (`.github/workflows/ci.yml`); the `pre-push` hook only prints a notice, never blocks (user's requirement). Two rule families were triaged finding-by-finding: `no-unenclosed-multiline-block` (11/11 false positives on the one-line guard style → off) and `super-linear-regex` (2 of 19 real, see [[project_redos_regex_class]] → demoted to warning). Don't re-triage those from scratch.

Never launch a browser automatically. Do NOT invoke the `/run` skill or Playwright unless the user explicitly asks to see the app running.

Never launch a browser for: CSS/design changes, text fixes, simple logic, dropdown menus, or any change verifiable through tsc alone.

**Why:** browser automation wastes tokens and time. User explicitly said "שמור על טוקנים תעבוד רזה". tsc clean = done.

**How to apply:** default to `tsc --noEmit` only. Never run `/run` skill proactively.

**Threshold for Playwright (2026-07-08 refinement):** reserve it for massive/critical multi-step flows with real risk — checkout end-to-end, payment, `decrementStock`/inventory, full register+login. Not for "any UI change," even interactive ones (e.g. a loading-indicator/spinner swap with disable-button state was judged NOT to need it — tsc + confirming the live dev server actually serves the changed markup/CSS was enough). User confirmed this calibration explicitly, so lean toward tsc+server-check first; only reach for Playwright when the change touches a money/inventory-critical flow or spans many pages at once.

**Playwright IS now installed (added 2026-07-10, devDependency + chromium)** — first crossed the threshold on the cart/stock-ceiling bug (spanned product card, both quick-view modals, product page, wishlist). Before that date it was deliberately not installed; don't re-derive the old "not installed" state from an outdated memory snapshot — check `package.json` if in doubt, but as of this writing it's there.

**Don't ask permission when the threshold is crossed (2026-07-10 clarification)** — user confirmed: in past sessions the install+run just happened as part of the task, no separate confirmation step, and that's the desired behavior going forward. So: below threshold → tsc only, never mention Playwright. At/above threshold → just `npm install -D playwright && npx playwright install chromium` and run it, silently, as one more step of the task — don't stop to ask "should I install Playwright?" or report BLOCKED for lacking it. A cart/stock/inventory bug that spans multiple add-to-cart surfaces (product card, quick-view modal, product page, wishlist) counts as crossing the threshold, same tier as the checkout/payment examples above.

**Two gotchas when a Playwright check IS warranted (learned 2026-07-29, checkout stock flow):** (1) verify against `npx astro build` + `node dist/server/entry.mjs` on a spare port (4399) — never the user's dev server ([[feedback_dev_server]]) — and re-kill+restart it after every rebuild, or the old process 404s on the new chunk hashes and every navigation just hangs. (2) **Headless Chromium never sets `document.hidden`** — opening a second page or `bringToFront()` fires no `visibilitychange`, so anything keyed to "returning to a left-open tab" silently never runs and the test reads as a product bug. Dispatch the event yourself (`document.dispatchEvent(new Event('visibilitychange'))`), and wait out real throttles (`cart-prices.ts` trusts an answer for 60s) instead of measuring the throttle. Also: a browser check against the real `data/*.json` CREATES dev data — back up the file first, then remove the test orders + their notifications/money-events, zero the day's `purchase` counter in `analytics-events.json`, clear `checkout-idempotency.json`, and restore stock. `data/` is gitignored, so there is no safety net.
