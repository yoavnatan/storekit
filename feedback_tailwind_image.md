Hard rules set by the user going forward:

1. **Tailwind CSS v4** for all new styling — no new CSS files, no `<style>` blocks. Existing CSS files stay until naturally touched.
   - **Escalated 2026-07-15 — "stop the snowball."** User discovered the codebase had ~7,300 lines of hand-written CSS across 24 files despite Tailwind being configured since project start (barely used — only 8/36 `.astro` files had utility classes), with a global `main.css` bundling all of it into every page load (measured: 25.5KB gzip on every single page, hurting Lighthouse's unused-CSS audit + first-load LCP for first-time SEO visitors). Trigger: a brand-new component (`AdminPager.astro`) got 2 lines of custom CSS instead of Tailwind utilities — exactly the small-increment drift to stop. Treat "convert existing CSS on contact" as a hard, proactive rule now, not a lazy one. `dashboard.css`/`store.css` (~3,300 lines combined, contain both page-specific AND shared-component rules mixed together) are queued as a *יום חמישי* (2026-07-16) item in CURRENT_TASK.md for a full untangle-then-convert pass.
   - **User asked whether full Tailwind adoption conflicts with the `tokens.css` CSS-variable color system — it does not.** Tailwind v4's own theming is CSS-variable-based (`@theme` generates `--color-*` vars); `tokens.css` already aligns with that model. Current usage is `[color:var(--color-X)]` arbitrary-value syntax; a cleaner end state would fold the tokens into an `@theme` block so utilities like `bg-accent` work natively. Don't re-raise "does Tailwind conflict with our vars" as an open question — already resolved, answer is no.
   - **Escalated again 2026-07-16 — rapid visual-iteration loops are the actual trigger.** A ~13-round rapid-fire session redesigning a homepage hero animation (each round driven by quick visual feedback — shape, size, motion) produced ~250+ new lines of hand-written CSS in `home.css` instead of Tailwind utility classes, even though the rule was read at session start. Root cause wasn't unclear instructions — it was losing the self-check discipline once absorbed in a fast feedback loop turn after turn. **The trap: "convert existing CSS on contact only" only exempts *old, pre-existing* rules you happen to touch — it is not license to keep adding brand-new plain CSS selectors for brand-new features**, even mid-iteration, even in an existing file. Before writing any new CSS selector, ask "can this be a Tailwind utility class on the element instead?" — true for `position`/`inset`/`display`/`flex`/`gap`/`padding`/`opacity`/`z-index`/`width`/`height`/`background-color`, `hover:`/`active:` states, and even `::before`/`::after` (Tailwind v4 `before:`/`after:` variants support arbitrary values). The one real exception is `@keyframes` block definitions themselves (can't be a utility class) — but their *application* still goes through a Tailwind animation utility: either a `@theme` block registering `--animate-<name>` (see `tokens.css`, used for `animate-modal-in` etc.) for reusable micro-interactions, or the arbitrary-value syntax `animate-[<keyframe>_<duration>_<easing>_<iteration>]` directly on the element (see `ProductQuickView.astro`'s `animate-[skeleton-shimmer_1.3s_infinite_linear]`) for one-off/page-specific ones. Only the raw `@keyframes {}` rule belongs in CSS — never a wrapping class that also carries properties Tailwind already covers.
2. **Astro `<Image />` from `astro:assets`** for all static platform images (store pages, product cards, product page). Dashboard upload widget keeps `<img>` for blob previews. JS template literals (modal HTML strings) also keep `<img>`.
3. **`passthroughImageService()`** is configured in `astro.config.mjs` — Cloudinary handles optimization via URL transforms, Astro `<Image />` enforces attrs (alt/width/height) and adds loading/decoding defaults.
4. **`cdnSrc(url, w?)` from `src/config/store.config.ts`** — adds `f_auto,q_auto,w_N` to Cloudinary URLs. Always use this as the `src` prop in `<Image />`. Sizes: cards=400, carousel=300, thumbs=128, product-main=800, related-products=340. Same size on every page for the same context = shared browser cache across pages.
5. **Mobile-first**: design for 375px, scale up with `sm:` / `md:` / `lg:`.
6. **Lighthouse 100 target**: first 4 products `loading="eager"`, first 2 `fetchpriority="high"`. Product page main image: `loading="eager" fetchpriority="high"`.
7. Keep components as **Astro server components** wherever possible.

**Why:** User requires Astro-native solutions before custom ones. passthroughImageService + cdnSrc is the correct architecture for Cloudinary + Astro SSR — avoids Sharp re-processing overhead and uses Cloudinary CDN directly.

**How to apply:** `import { Image } from 'astro:assets'` + `import { cdnSrc } from '../../config/store.config.js'`. Never use plain `<img>` for static product/store images. Related: [[project-seo-priority]], [[feedback-mobile-first]], [[feedback-architecture]].
